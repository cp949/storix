# 스키마 마이그레이션 롤백은 자동화하지 않고, 이미지 되돌리기(스키마 불변경)와 백업 복구(스키마 변경)로만 처리한다

DEPLOY-03(업그레이드 경로 문서화)에서 실패 대응 범위를 정하며 나온 결정이다. TypeORM은
`migration:revert`로 down 마이그레이션 실행을 지원하고, 기존 마이그레이션 5개 모두
`down()`을 구현해뒀지만, 이 리포는 `migration:revert`/`migration:revert:prod` 스크립트를
추가하지 않는다. 업그레이드 실패는 두 갈래로 나뉜다: (1) 새 이미지에 버그가 있지만
마이그레이션이 스키마를 바꾸지 않은 경우 — 이전 이미지(커밋)로 되돌리면 끝난다.
(2) 스키마 변경 마이그레이션까지 실행된 뒤 문제가 발견된 경우 —
`docs/deployment/backup-restore.md`의 업그레이드 전 백업에서 복구한다. `down()`을
검증·유지보수 대상에 넣는 비용(마이그레이션마다 순방향과 같은 신뢰도로 역방향도
작성·테스트해야 함) 대비, ADR-0015가 이미 확립한 백업/복구 절차를 재사용하는 쪽이
싸다.

## Considered Options

- **`migration:revert`/`migration:revert:prod` 스크립트 추가, down() 자동 테스트
  포함**: 스키마 변경만 되돌리면 되는 경우 백업 복구보다 빠르고 데이터 손실도 없다.
  하지만 마이그레이션마다 순방향·역방향 양쪽을 같은 신뢰도로 유지해야 하고
  `migrations.integration-spec.ts`도 revert 경로까지 커버해야 해 유지보수 비용이
  늘어난다. 단일 고객 인스턴스 규모에서 이 비용 대비 실익이 낮다고 보류했다(OPS-02
  때 PITR을 보류한 논리와 동일).
- **아무 문서도 남기지 않고 사안별 판단**: `backup-restore.md`가 이미 있는데 이
  결정을 기록하지 않으면, 다음 사람이 "TypeORM은 revert를 지원하는데 왜 스크립트가
  없지?"를 다시 조사하게 된다.

## Consequences

- 새 마이그레이션에 `down()`을 작성할 의무는 없다 — 실행 경로가 없어 검증되지
  않는 코드를 유지보수 대상에 남기지 않는다. 기존 5개의 `down()`은 제거 비용 대비
  실익이 없어 그대로 둔다.
- `docs/deployment/upgrade.md`는 실패 대응을 "이번 마이그레이션이 스키마를
  바꿨는가"로 분기한다 — 운영자가 매 업그레이드마다 이를 확인해야 한다.
