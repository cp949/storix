# 스키마 마이그레이션 롤백은 자동화하지 않고, 이미지 되돌리기(스키마 불변경)와 백업 복구(스키마 변경)로만 처리한다

`DEPLOY-03`은 업그레이드 실패 대응을 다음과 같이 나눈다.

| 조건                                         | 대응                             |
| -------------------------------------------- | -------------------------------- |
| 새 이미지에 버그가 있고 스키마는 바뀌지 않음 | 이전 이미지(커밋)로 되돌린다.    |
| 스키마 변경 마이그레이션 실행 후 문제 발견   | 업그레이드 전 백업에서 복구한다. |

백업 복구는 `docs/deployment/backup-restore.md`를 따른다.

## 결정 근거

- TypeORM은 `migration:revert`로 down 마이그레이션을 지원한다.
- 채택 당시 기존 마이그레이션은 모두 `down()`을 구현했다.
- 이 저장소는 `migration:revert`/`migration:revert:prod` 스크립트를 추가하지 않는다.
- down 경로를 지원하려면 순방향과 같은 신뢰도로 작성·검증해야 한다.
- api ADR-0015의 백업/복구를 재사용하는 편이 유지 비용이 낮다고 판단했다.

## Considered Options

- **revert 스크립트와 `down()` 자동 테스트 추가**
  - 스키마 변경만 되돌리는 경우에는 백업 복구보다 빠를 수 있다.
  - 데이터 손실 여부는 해당 down 마이그레이션에 달려 있다.
  - 순방향·역방향을 모두 유지해야 한다.
  - `migrations.integration-spec.ts`에도 revert 경로 검증이 필요하다.
  - 단일 고객 인스턴스에서 비용 대비 실익이 낮다고 판단해 보류했다.
  - `OPS-02`에서 PITR을 보류한 근거와 같다.
- **문서 없이 사안별 판단**
  - TypeORM이 지원하는 revert 스크립트가 없는 이유를 반복 조사하게 된다.
  - 기존 `backup-restore.md`와 함께 실패 대응 결정을 기록한다.

## Consequences

- 새 마이그레이션에 `down()`을 작성할 의무는 없다.
- 실행·검증 경로가 없는 코드를 유지 대상으로 추가하지 않는다.
- 채택 당시 기존 `down()`은 제거 실익이 낮아 유지한다.
- `docs/deployment/upgrade.md`는 스키마 변경 여부로 실패 대응을 나눈다.
- 운영자는 업그레이드마다 스키마 변경 여부를 확인한다.
