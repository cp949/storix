# 서비스 간 인증은 정적 API 키 슬라이스 비교로 구현한다

## 인증 방식

호출 서버 인증 계층이 없던 Storix API에 정적 키 인증을 도입한다(SEC-01).

- 요청 헤더는 `Authorization: Bearer <key>`를 사용한다.
- 요청 키를 환경변수의 유효 키 목록과 비교한다.
- 전역 Guard(NestJS `APP_GUARD`)로 적용한다.
- 헬스체크(`/health/live`, `/health/ready`)는 인증에서 제외한다.

## 키 관리와 로테이션

키는 배포 전체가 공유한다.

- `STORIX_API_KEY`(기존 표기 `API_KEY`): 필수인 현재 유효 키.
- `STORIX_API_KEY_PREVIOUS`(기존 표기 `API_KEY_PREVIOUS`): 로테이션 중에 사용하는 선택적 이전 키.
- 요청 키가 둘 중 하나와 일치하면 인증을 통과한다.
- 키 교체 시 프로세스를 재시작한다.
- 핫리로드는 구현하지 않는다.

재시작 배포 윈도우에는 신·구 키를 모두 허용한다.
이 기간에 호출 서버가 키를 전환해도 요청 인증을 유지하기 위한 방식이다.

## 인증 실패

- 키 누락과 불일치를 구분하지 않고 401을 반환한다.
- 상세 사유는 구조화 로그에만 기록한다.

무차별 대입 시도에 실패 사유를 노출하지 않기 위한 결정이다.

## Considered Options

- **HMAC 요청 서명**
  - imgproxy의 `IMGPROXY_KEY`/`IMGPROXY_SALT`처럼 키와 솔트로 요청을 서명하는 방식이다.
  - 요청 위변조를 방지할 수 있다.
  - Storix API 인증보다 presigned download URL(`STORAGE-02`)에 더 적합하다고 판단해 보류했다.
- **클라이언트별 개별 키 발급**
  - 호출자를 구분할 수 있어 감사 로그에 유리하다.
  - Storix는 고객별 단일 인스턴스 배포를 목표로 한다.
  - 멀티테넌트 배포나 여러 호출 서버를 요구하지 않았다.
  - 검토 시점에는 복잡도 증가를 감수할 근거가 없어 보류했다.

## 한계와 재검토 조건

- 단일 공유 키 인증만으로는 호출자를 구분할 수 없다.
- `SEC-04`(감사 로그)에서 호출자 식별이 필요해지면 이 결정을 재검토한다.
