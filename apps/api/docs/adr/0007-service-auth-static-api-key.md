# 서비스 간 인증은 정적 API 키 슬라이스 비교로 구현한다

Storix API는 지금까지 호출 서버를 검증하는 인증 계층이 없었다(SEC-01). 요청 헤더
`Authorization: Bearer <key>`로 전달된 키를 환경변수로 관리하는 유효 키 목록과
비교하는 정적 키 인증을 전역 Guard(NestJS `APP_GUARD`)로 붙인다. 헬스체크
(`/health/live`, `/health/ready`)만 이 인증에서 예외로 둔다.

키는 배포 전체가 공유하는 단일 키 쌍을 쓴다. `API_KEY`(필수, 현재 유효 키)와
`API_KEY_PREVIOUS`(선택, 로테이션 중인 이전 키) 두 환경변수로 나눠 관리하고, 요청 키가
둘 중 하나와 일치하면 인증을 통과시킨다. 키 교체는 프로세스 재시작을 허용하되(핫리로드는
만들지 않는다), 재시작 배포 윈도우 동안 신·구 키가 모두 유효하므로 그 사이 들어오는
요청이 실패하지 않는다 — 이 슬라이스가 곧 무중단 로테이션 메커니즘이다.

인증 실패는 사유(키 없음/불일치/이전 키에도 없음)를 구분하지 않고 401만 반환한다.
무차별 대입 시도에 힌트를 주지 않기 위함이며, 상세 사유는 구조화 로깅에만 남긴다.

## Considered Options

- **HMAC 요청 서명** (imgproxy의 `IMGPROXY_KEY`/`IMGPROXY_SALT`처럼 키+솔트로 요청을
  서명해 위변조까지 막는 방식): 위조 방지 이점은 있지만, Storix API 자체보다는
  presigned download URL(`STORAGE-02`)에 더 맞는 성격이라 이번 범위에서는 보류했다.
- **클라이언트별 개별 키 발급**: 호출자를 구분할 수 있어 감사 로그에 유리하지만,
  Storix의 목표가 고객별 단일 인스턴스 배포(멀티테넌트 아님)이고 지금 시점에 호출
  서버가 여럿이어야 한다는 요구가 없어 복잡도만 늘어난다고 보고 보류했다.

단일 공유 키를 택했으므로 이 인증 계층만으로는 "누가" 호출했는지 구분할 수 없다.
`SEC-04`(감사 로그)를 구현할 때 호출자 식별이 실제로 필요해지면 이 결정을
재검토해야 한다.
