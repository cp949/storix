# 감사 로그의 호출자 식별은 자기신고 비인증 값을 사용한다

## 결정

- 호출 서버는 `X-Caller-Id` 헤더로 호출자 식별값을 자기신고한다.
- 감사 로그는 이 값을 `caller` 필드에 기록한다.
- Storix는 식별값의 진위를 검증하지 않는다.
- 헤더가 없거나 형식이 유효하지 않으면 `caller`는 `null`이다.
- 형식은 `resolveCallerId()`에서 검증한다(`audit-log.interceptor.ts`).

## 결정 근거

- `SEC-04`는 누가, 언제, 어떤 namespace·경로에 접근했는지 기록하도록 요구한다.
- api ADR-0007의 인증은 배포 전체가 공유하는 단일 정적 API 키를 사용한다.
- 이 인증 계층만으로는 호출자를 구분할 수 없다.
- 서비스별 API 키 발급 대신 자기신고 값을 기록한다.

## Considered Options

- **호출자 식별 생략**
  - `caller` 필드를 생략하거나 고정값으로 채우는 안이다.
  - api ADR-0007의 인증 결정을 유지할 수 있다.
  - 로드맵의 호출자 기록 요구를 충족하지 못해 보류했다.
- **서비스별 API 키 발급(api ADR-0007 재검토)**
  - 키마다 caller 이름을 연결하면 검증된 식별자를 확보할 수 있다.
  - api ADR-0007은 고객별 단일 인스턴스 배포를 전제로 이 안을 보류했다.
  - 여러 호출 서버가 필요하다는 요구도 없었다.
  - 전제가 바뀌지 않아 인증 계층 변경은 `SEC-04` 범위에서 제외했다.

## 신뢰도와 재검토 조건

- 자기신고 값은 위조할 수 있다.
- 보안 감사 증거로서 신뢰도가 제한적이다.
- 호출 서버가 늘어나거나 위조 방지가 필요해지면 api ADR-0007과 함께 재검토한다.

## 알려진 한계

`audit_log`는 모든 요청의 완전한 기록이 아니다.

### 감사 로그에 남지 않는 요청

다음 요청은 `AuditLogInterceptor`에 도달하지 않고 `audit_log`에도 기록되지 않는다.

- body-parser가 거부한 요청(잘못된 JSON, 413).
- 라우트가 없는 요청.

누락 원인:

- body-parser 오류와 없는 라우트는 Nest 인터셉터 파이프라인 전에 처리된다.

### 인증 거부(401)

`ApiKeyGuard`가 거부한 요청은 인터셉터에 도달하지 않는다.
NestJS가 Guard를 Interceptor보다 먼저 실행하기 때문이다.
대신 `DomainErrorFilter`가 `InvalidApiKeyError`를 받아 `audit_log`에 기록한다(RQ-019).
키가 없는 요청과 잘못된 키로 거부된 요청을 구분하지 않는다.
인증 실패 사유는 `ApiKeyGuard`의 구조화 로그에도 남는다(`api-key.guard.ts`).

401 기록 규칙:

- 기록은 응답을 막지 않는 best-effort다. 저장이 실패해도 401 응답은 그대로 나간다.
- `caller`와 `namespace_id`는 `null`이다. 인증 전이므로 자기신고 값도 쓰지 않는다.
- `path`는 `request.path`를 `sanitizeAuditString`으로 정리해 4096 코드 유닛까지 저장한다. `operation`은 `<method> <path>`를 128자로 자른 값이다.
- 인증되지 않은 요청은 호출자가 수를 정하므로 윈도당 상한을 둔다. 상한은 프로세스당 60초에 60행이다(`auth-reject-audit-limiter.ts`).
- 상한을 넘은 거부는 행을 만들지 않고 건수만 센다. 윈도당 첫 생략 때 경고 로그를 한 번 남긴다.
- 다음 윈도의 첫 거부가 오면 직전 윈도의 생략 건수를 요약 행 1개로 기록한다. 요약 행은 `operation='AUTH_REJECT_SUPPRESSED'`, `status=401`, `path=null`, `detail={suppressed, windowSeconds}`이고, 그 거부의 `request_id`를 쓴다.
- 윈도당 최대 행 수는 개별 행 60개와 요약 행 1개다.
- 상한과 윈도는 환경변수로 바꿀 수 없다.

401 기록의 한계:

- 타이머를 쓰지 않으므로 마지막 윈도의 요약 행은 다음 거부가 올 때까지 기록되지 않는다. 그 건수는 경고 로그에서만 확인할 수 있다.
- 상한은 프로세스 단위다. 인스턴스가 여러 개이면 인스턴스 수만큼 늘어난다.
- 상한을 넘은 시간대의 개별 요청 ID, 경로, 시각은 `audit_log`에 없다.

### 보존 정책

`audit_log`를 삭제하거나 보존 기간을 적용하는 코드는 없다.
행은 계속 쌓인다. 크기 관리는 운영자 몫이다.
보존 정책은 별도 결정이 필요하다.

### 누락 요청까지 기록하려면

body-parser 거부와 없는 라우트까지 기록하려면 Guard보다 먼저 실행하는 미들웨어에서 훅을 걸어야 한다.
이 재설계는 `SEC-04` 범위 밖의 후속 작업이다.
