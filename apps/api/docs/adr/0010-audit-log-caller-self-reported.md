# 감사 로그의 호출자 식별은 자기신고 비인증 값을 사용한다

SEC-04(감사 로그)는 누가/언제/어떤 namespace·경로에 접근했는지 기록해야
하지만, ADR-0007이 이미 지적했듯 인증이 배포 전체가 공유하는 단일 정적 API
키라서 인증 계층만으로는 호출자를 구분할 수 없다. 이 문제를 풀기 위해
서비스별 API 키 발급(ADR-0007 재검토)으로 전환하는 대신, 호출 서버가 요청
헤더(`X-Caller-Id`)로 자기신고하는 비인증 식별값을 감사 로그의 `caller`
필드에 그대로 기록하는 방식을 택했다. Storix는 이 값의 진위를 검증하지
않으며, 헤더가 없으면 `caller`는 `null`로 남는다.

## Considered Options

- **호출자 식별 도입 안 함**: `caller` 필드를 생략하거나 고정값으로 채운다.
  ADR-0007의 인증 결정은 그대로 두지만, 로드맵이 명시한 "누가" 요구사항을
  전혀 충족하지 못해 감사 로그의 실효성이 떨어진다고 보고 보류했다.
- **서비스별 API 키 발급(ADR-0007 재검토)**: 키마다 caller 이름을 태깅하면
  검증된 식별자를 확보할 수 있지만, ADR-0007이 이미 "고객별 단일 인스턴스
  배포이고 호출 서버가 여럿이어야 한다는 요구가 없다"는 이유로 보류한
  결정이다. 그 전제가 바뀌지 않았으므로 인증 계층 자체를 다시 여는 것은
  이번 티켓 범위를 벗어난다고 보고 보류했다.

자기신고 값은 위조 가능하므로 보안 감사 증거로서의 신뢰도는 제한적이다.
호출 서버가 여러 개로 늘어나거나 위조 방지가 실제로 필요해지면 ADR-0007과
함께 재검토한다.

## 알려진 한계: 인증 실패/파싱 실패 요청은 감사 로그에 남지 않는다

NestJS는 Guard를 Interceptor보다 먼저 실행하므로, `ApiKeyGuard`가 거부한 요청(401)은
`AuditLogInterceptor`에 도달하지 않아 `audit_log`에 남지 않는다. 마찬가지로 body-parser
단계에서 거부되는 요청(잘못된 JSON, 413)과 라우트 자체가 없는 요청도 Nest의 인터셉터
파이프라인 전에 걸러져 감사 로그 대상이 아니다. 인증 실패 자체는 `ApiKeyGuard`가 별도로
구조화 로깅(`api-key.guard.ts`)하므로 정보 자체가 유실되지는 않지만, `audit_log` 테이블을
"모든 요청의 완전한 기록"으로 오해하면 안 된다. 이 갭을 메우려면 인터셉터가 아니라
미들웨어(Guard보다 먼저 실행됨) 레벨에서 훅을 거는 재설계가 필요하며, 이번 SEC-04 범위
밖의 후속 작업으로 남긴다.
