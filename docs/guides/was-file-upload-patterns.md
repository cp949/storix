# WAS에서 업무 데이터와 파일 저장하기

Storix를 사용하는 WAS가 폼 제출과 파일 업로드를 구현할 때 선택할 수 있는 두 가지 패턴입니다. **파일을 먼저 업로드하고, 제출 때 파일 ID만 연결하는 2번 패턴을 권장합니다.** 제출 요청이 파일 전송에 묶이지 않고, 업무 데이터와 파일 연결을 WAS DB에서 함께 확정할 수 있습니다.

Storix는 파일 저장·조회·삭제와 생성 시 지정된 만료 회수를 제공합니다. 사용자 권한, 업무 데이터, 업무상 파일 사용 여부와 그에 따른 정리는 WAS가 관리합니다. 만료를 지정하지 않은 임시 파일도 업무 정책에 따라 WAS가 정리해야 합니다. Storix 파일 변경과 WAS DB commit은 함께 묶이지 않으므로, 어느 패턴이든 실패하거나 중단된 요청을 정리할 절차가 필요합니다.

|                       | 1. 제출하면서 파일 전송                         | 2. 먼저 업로드하고 ID 제출         |
| --------------------- | ----------------------------------------------- | ---------------------------------- |
| 사용자의 제출 요청    | 업무 필드 + 파일 바이트 (`multipart/form-data`) | 업무 필드 + 이미 업로드한 `fileId` |
| 제출 중 Storix 업로드 | 수행                                            | 수행하지 않음                      |
| WAS DB의 파일 상태    | 업로드 중·실패·연결 완료 등을 추적              | 업로드 중·임시·연결 완료 등을 추적 |
| 정리 대상             | 업무 DB에 연결되지 않은 업로드                  | 제출하지 않고 남은 임시 업로드     |

## 공통 준비

WAS는 사용자 인증·권한과 파일 정책을 검사하고, 자신의 서비스 자격으로 Storix를 호출하세요. 브라우저가 보낸 파일 ID를 권한 증명으로 사용하지 마세요.

이 문서의 `fileId`는 Storix FILE 노드의 UUID, 즉 업로드 응답의 `id`입니다. Storix의 일반 파일 API는 namespace와 경로를 사용하므로 WAS는 `fileId`와 함께 `namespaceId`, `path`, 소유자, 업무 용도를 기록하세요. 파일을 이동하면 보관한 경로도 갱신하세요. 삭제 전에는 보관한 경로의 현재 파일 ID를 확인하고, 확인과 삭제 사이에 같은 경로를 다른 파일이 차지하지 않도록 운영하세요.

업로드에는 파일마다 고유한 경로를 배정하세요. 이미 사용 중인 경로를 덮어쓰지 않아야 한다면 Storix의 조건부 콘텐츠 업로드를 사용하세요. 새 업로드를 시작하기 전에 WAS DB에 업로드 시도와 예정 경로를 기록해 두면, Storix 저장 성공 직후 WAS가 중단되어도 정리 대상을 찾을 수 있습니다.

## 1. 사용자가 제출하면서 파일 바이트를 보내는 경우

브라우저는 업무 필드와 파일을 `multipart/form-data`로 **WAS에** 보냅니다. WAS는 파일 바이트를 Storix 콘텐츠 API로 전달합니다. Storix에 multipart 폼 전체를 전달하는 방식은 아닙니다.

```text
브라우저 → WAS: 업무 필드 + 파일 바이트
WAS → Storix: 파일 업로드
Storix → WAS: fileId, path
WAS → WAS DB: 업무 레코드 + 파일 참조 commit
WAS → 브라우저: 제출 결과
```

권장 처리 순서:

1. WAS가 권한·업무 필드·파일 개수·크기·형식을 검사합니다.
2. 각 파일의 업로드 시도, 고유 경로, 상태(예: `UPLOADING`)를 WAS DB에 먼저 기록합니다.
3. WAS가 Storix에 업로드하고, 성공한 파일의 `fileId`와 경로를 기록합니다. 실패한 파일은 실패 상태와 원인을 기록합니다.
4. 필요한 파일이 모두 업로드되면 업무 레코드와 파일 참조를 하나의 WAS DB 트랜잭션으로 저장하고 업로드 기록을 연결 완료로 바꿉니다. DB commit을 확인한 뒤에만 제출 성공을 반환합니다.

**보상과 실패 처리:** 여러 파일 중 하나가 실패하면 이미 업로드된 파일을 삭제해야 합니다. Storix 업로드 후 업무 DB commit이 실패한 경우에도 같은 보상이 필요합니다. 삭제 요청 자체가 실패하거나 WAS가 도중에 종료될 수 있으므로, 즉시 삭제 시도만으로 끝내지 말고 삭제 대상을 DB에 남겨 재시도하세요. DB commit 결과가 불명확하면 먼저 실제 업무 레코드와 파일 참조를 조회한 뒤 미참조 파일만 삭제하세요. 요청을 재시도할 때 중복 업무 생성·중복 업로드를 막는 규칙도 WAS에서 정하세요.

**주기적 cleanup:** 오래 지속된 업로드 중·실패·삭제 대기 기록을 스캔하고, 해당 경로의 Storix 파일 존재 및 WAS DB 참조를 확인하세요. 참조되지 않은 파일은 삭제하고 실패한 삭제는 다음 실행에서 재시도하세요. 업로드 성공 직후 상태 기록 전에 중단된 파일도 찾을 수 있도록, 먼저 기록한 예정 경로 또는 업로드 전용 경로 구간을 대조하세요.

이 방식은 한 번의 제출 요청으로 처리할 수 있지만, 업로드 상태 기록, 보상 삭제, 실패 재시도, 주기적 cleanup까지 구현해야 합니다. 파일 전송 시간이 제출 응답 시간에도 포함됩니다.

## 2. 먼저 업로드하고 제출 때 파일 ID를 보내는 경우 — 권장

파일 선택 시 WAS의 별도 업로드 API를 호출하세요. WAS가 Storix에 저장하고 업로드 결과를 자신의 DB에 `TEMP`로 기록한 뒤 `fileId`를 브라우저에 반환합니다. `TEMP`는 **WAS DB의 상태**입니다.

```text
파일 선택: 브라우저 → WAS → Storix 업로드 → WAS DB에 TEMP 기록 → fileId 반환
제출: 브라우저 → WAS: 업무 필드 + fileIds → WAS DB에서 연결·확정
```

권장 처리 순서:

1. 선 업로드 전에 WAS가 사용자 권한과 파일 정책을 검사하고 업로드 시도·예정 경로를 기록합니다. Storix 업로드 성공 후 `fileId`, `namespaceId`, `path`, 소유자, 생성 시각과 `TEMP` 상태를 저장합니다. 이 기록이 끝난 뒤 `fileId`를 반환합니다.
2. 사용자가 제출하면 WAS는 모든 `fileId`의 존재, 소유자, namespace, 업무 용도, 상태를 검증합니다. 새로 연결할 파일은 사용 가능한 `TEMP` 상태여야 합니다. 수정 요청에서 유지할 기존 파일은 해당 업무 레코드에 이미 연결되어 있는지도 확인합니다.
3. 하나의 WAS DB 트랜잭션에서 업무 레코드와 파일 연결을 저장하고, 새로 연결한 파일을 `TEMP`에서 `ACTIVE`로 바꿉니다. 제출 처리 중에는 Storix에 업로드하지 않습니다. DB 작업이 실패하면 업무 레코드·연결·상태 변경이 함께 rollback됩니다.

**미제출 파일 자동 삭제:** 사용자가 업로드만 하고 제출하지 않을 수 있습니다. WAS가 `TEMP`의 보관 기한을 정하고, 기한이 지난 파일은 새 제출에 연결할 수 없게 처리하세요. 주기적 cleanup 작업은 제출 처리와 경합하지 않도록 대상 상태를 점유하고, 다른 업무 참조가 없는지 확인한 뒤 Storix에 삭제를 요청합니다. 삭제 실패는 기록해 재시도하고, 성공 후 WAS DB 기록을 정리하세요. 예를 들어 24시간은 WAS가 선택할 수 있는 보관 정책일 뿐 Storix의 파일 만료 설정이 아닙니다.

선 업로드에도 Storix 저장 성공 후 WAS DB 기록 실패·프로세스 중단이 생길 수 있습니다. 이 경우 먼저 남긴 업로드 시도와 경로를 이용해 미참조 파일을 찾고 삭제하세요. 이 cleanup은 미제출 `TEMP` 정리와 별도로 놓치지 않아야 합니다.

### Storix 파일 만료와 확정 계약

Storix는 새 FILE의 생성 시점에 만료 초를 받을 수 있습니다. 조건부 콘텐츠 업로드에는 `X-If-Absent: true`와 `X-Expires-In`을 함께 보내고, 재개 업로드 세션 생성에는 `ifAbsent: true`와 `expiresInSeconds`를 함께 보냅니다. 기본 허용 범위는 60~2592000초이며 서버 설정으로 조정할 수 있습니다. 만료 시각은 응답의 `expiresAt`에서 확인할 수 있습니다. 업로드 세션의 만료 시각과 완료된 FILE의 만료 시각은 별개입니다.

기본 순서에서 호출자는 FILE을 참조하는 자체 영속 상태와 `persist` 재시도 작업을 같은 커밋에 기록해야 합니다. 그 커밋이 성공한 뒤 Storix에 확정을 요청하고, 성공할 때까지 저장된 작업을 재시도합니다. 자체 상태를 확정하기 전에 파일 만료를 해제하면 자체 커밋 실패 후에도 미참조 파일이 남을 수 있습니다.

업로드 직후 파일 경로·node ID를 자체 DB에 임시 기록으로 남기고 그 기록을 기한 뒤 정리하는 WAS는 순서를 바꿀 수 있습니다. 확정을 먼저 요청하고, 성공한 뒤 업무 데이터와 파일 연결을 commit합니다. 확정이 실패하면 commit하지 않으므로 업무 데이터가 만료 예정 파일을 가리키지 않습니다. 확정 뒤 commit이 실패하면 확정된 파일이 임시 기록으로 남고, 임시 기록 정리가 이를 삭제합니다. 이 순서에는 만료 전에 끝나야 하는 확정 재시도 작업이 필요 없습니다.

만료를 해제하려면 `POST /api/v2/namespaces/{namespaceId}/fs/mutations`에 `{ "kind": "persist", "path": "/example.bin", "ifRevision": "r1.…" }`를 보냅니다. `Idempotency-Key`와 `X-Mutation-Scope`가 필요합니다. 성공하면 revision이 바뀌고 `expiresAt`이 null이 됩니다. 이미 만료가 없다면 변경 없이 성공합니다. 같은 key의 재시도는 최초 결과를 재생합니다. 성공 응답을 잃은 뒤 새 key로 재시도해 412를 받으면 `current.id`가 같은 FILE이고 `current.expiresAt`이 null인지 확인해 확정 완료를 판정할 수 있습니다.

만료 시각이 지나도 GC가 삭제하기 전에는 조회와 확정이 가능합니다. GC 삭제는 namespace의 휴지통 정책을 따르며 휴지통의 기본값은 OFF입니다. 만료를 해제하지 않은 FILE은 GC가 삭제할 수 있으므로 필요한 FILE의 확정 누락은 데이터 유실로 이어집니다. PUBLIC namespace의 인증 없는 콘텐츠 조회와 다운로드는 만료 예정 FILE을 404로 숨깁니다.

## 기존 첨부파일을 제거할 때

업무 수정이나 삭제에서 기존 파일을 제거한다면 먼저 WAS DB의 파일 연결 변경을 commit하세요. 다른 업무에서 사용하지 않는 파일만 Storix에 삭제 요청을 보내고, 실패하면 재시도할 작업으로 기록하세요. DB commit 전에 파일부터 삭제하면 rollback 후 업무 레코드가 삭제된 파일을 가리킬 수 있습니다.

## Storix API 대응

- 파일 업로드: `POST /api/v2/namespaces/{namespaceId}/fs/content?path=...`는 파일 바이트를 받고 성공 응답에 `id`와 `path`를 포함합니다. 새 파일만 허용할 때는 기존 `fs/content/conditional` 계약을 확인하세요.
- 파일 만료 지정: `POST .../fs/content/conditional`의 `X-Expires-In` 또는 `POST .../fs/upload-sessions`의 `expiresInSeconds`를 사용합니다. 둘 다 새 FILE 조건에서만 허용됩니다.
- 파일 확정: `POST .../fs/mutations`의 `persist`는 `ifRevision`이 일치하는 FILE의 만료를 해제합니다.
- 파일 확인: `GET /api/v2/namespaces/{namespaceId}/fs/stat?path=...`에서 현재 `id`를 확인할 수 있습니다.
- 파일 삭제: `POST /api/v2/namespaces/{namespaceId}/fs/rm?path=...`는 경로를 대상으로 하며 삭제 결과는 Storix 휴지통 계약을 따릅니다.
- 큰 파일의 선 업로드에는 기존 재개 업로드 기능을 사용할 수 있습니다. 그 기능의 세션 만료는 **완료 전 업로드 세션**에 적용되며, 완료된 FILE의 만료는 별도 `expiresInSeconds` 입력으로 지정합니다.

API 요청 형식은 [OpenAPI](../../apps/api/openapi.yaml), 파일 삭제 동작은 [휴지통과 복구](../design/09-vfs-trash-and-recovery.md)를 참고하세요. 이 문서의 WAS DB 상태와 cleanup은 사용처의 구현 예시이며 Storix 기능이 아닙니다.
