# WAS에서 업무 데이터와 파일 저장하기

**파일을 먼저 업로드하고 제출 때 파일 ID만 연결하는 2번 패턴을 권장한다.**

- 제출 요청에 파일 전송을 포함하지 않는다.
- 업무 데이터와 파일 연결을 WAS DB에서 함께 확정한다.

|                       | 1. 제출하면서 파일 전송                         | 2. 먼저 업로드하고 ID 제출         |
| --------------------- | ----------------------------------------------- | ---------------------------------- |
| 사용자의 제출 요청    | 업무 필드 + 파일 바이트 (`multipart/form-data`) | 업무 필드 + 이미 업로드한 `fileId` |
| 제출 중 Storix 업로드 | 수행                                            | 수행하지 않음                      |
| WAS DB의 파일 상태    | 업로드 중·실패·연결 완료 등을 추적              | 업로드 중·임시·연결 완료 등을 추적 |
| 정리 대상             | 업무 DB에 연결되지 않은 업로드                  | 제출하지 않고 남은 임시 업로드     |

책임 구분:

| 담당   | 책임                                                         |
| ------ | ------------------------------------------------------------ |
| Storix | 파일 저장·조회·삭제, 생성 시 지정한 만료에 따른 회수         |
| WAS    | 사용자 권한·업무 데이터·파일 사용 여부·업무 정책에 따른 정리 |

Storix 파일 변경과 WAS DB commit은 하나의 트랜잭션으로 묶이지 않는다.
두 패턴 모두 실패·중단된 요청의 정리 절차가 필요하다.
만료를 지정하지 않은 임시 파일도 WAS가 업무 정책에 따라 정리한다.

## 공통 준비

인증·파일 정책:

- WAS가 사용자 인증·권한과 파일 정책을 검사한다.
- WAS의 서비스 자격으로 Storix를 호출한다.
- 브라우저가 보낸 파일 ID는 권한 증명이 아니다.

파일 참조 관리:

- 이 문서의 `fileId`는 Storix FILE 노드의 UUID다.
- 업로드 응답의 `id`를 사용한다.
- 일반 파일 API는 namespace와 경로를 사용한다.
- WAS DB에 `fileId`·`namespaceId`·`path`·소유자·업무 용도를 기록한다.
- 파일을 이동하면 저장한 경로도 갱신한다.
- 삭제 전에는 해당 경로의 현재 파일 ID를 확인한다.
- 확인과 삭제 사이에 다른 파일이 같은 경로를 차지하지 않도록 운영한다.

업로드 준비:

1. 파일마다 고유한 경로를 배정한다.
2. 기존 경로를 덮어쓰면 안 되는 요청은 조건부 콘텐츠 업로드를 사용한다.
3. Storix 호출 전에 업로드 시도와 예정 경로를 WAS DB에 기록한다.

예정 경로가 있으면 Storix 저장 직후 WAS가 중단돼도 정리 대상을 찾을 수 있다.

## 1. 사용자가 제출하면서 파일 바이트를 보내는 경우

브라우저는 업무 필드와 파일을 `multipart/form-data`로 **WAS에** 보낸다.
WAS는 파일 바이트만 Storix 콘텐츠 API로 전달한다.

```text
브라우저 → WAS: 업무 필드 + 파일 바이트
WAS → Storix: 파일 업로드
Storix → WAS: fileId, path
WAS → WAS DB: 업무 레코드 + 파일 참조 commit
WAS → 브라우저: 제출 결과
```

권장 처리 순서:

1. 권한·업무 필드·파일 개수·크기·형식을 검사한다.
2. 파일별 업로드 시도·고유 경로·상태(예: `UPLOADING`)를 WAS DB에 기록한다.
3. Storix에 파일을 업로드한다.
   - 성공하면 `fileId`와 경로를 기록한다.
   - 실패하면 상태와 원인을 기록한다.
4. 필요한 파일이 모두 업로드되면 WAS DB 트랜잭션을 실행한다.
   - 업무 레코드와 파일 참조를 함께 저장한다.
   - 업로드 기록을 연결 완료로 바꾼다.
5. DB commit을 확인한 뒤 제출 성공을 반환한다.

보상·실패 처리:

| 상황                            | 처리                                                     |
| ------------------------------- | -------------------------------------------------------- |
| 여러 파일 중 하나가 업로드 실패 | 이미 업로드한 파일을 삭제한다                            |
| 업로드 후 업무 DB commit 실패   | 업로드한 파일을 삭제한다                                 |
| 삭제 요청 실패·WAS 중단         | 삭제 대상을 DB에 남겨 재시도한다                         |
| DB commit 결과 불명확           | 업무 레코드·파일 참조를 조회한 뒤 미참조 파일만 삭제한다 |
| 요청 재시도                     | WAS의 규칙으로 중복 업무 생성·중복 업로드를 막는다       |

주기적 cleanup:

1. 오래된 업로드 중·실패·삭제 대기 기록을 스캔한다.
2. Storix 파일 존재 여부와 WAS DB 참조를 확인한다.
3. 미참조 파일을 삭제한다.
4. 삭제 실패는 다음 실행에서 재시도한다.

예정 경로 또는 업로드 전용 경로 구간도 대조한다.
업로드 성공 후 상태를 기록하기 전에 중단된 파일을 찾기 위한 절차다.

이 패턴은 한 번의 제출 요청으로 처리한다.
파일 전송 시간은 제출 응답 시간에 포함된다.
업로드 상태 기록·보상 삭제·실패 재시도·주기적 cleanup을 구현해야 한다.

## 2. 먼저 업로드하고 제출 때 파일 ID를 보내는 경우 — 권장

파일 선택 시 WAS의 별도 업로드 API를 호출한다.
WAS는 Storix에 파일을 저장한다.
업로드 결과를 자신의 DB에 `TEMP`로 기록한 뒤 `fileId`를 반환한다.
`TEMP`·`ACTIVE`는 **WAS DB의 상태**다.

```text
파일 선택: 브라우저 → WAS → Storix 업로드 → WAS DB에 TEMP 기록 → fileId 반환
제출: 브라우저 → WAS: 업무 필드 + fileIds → WAS DB에서 연결·확정
```

권장 처리 순서:

1. 사용자 권한과 파일 정책을 검사한다.
2. 업로드 시도·예정 경로를 WAS DB에 기록한다.
3. Storix에 업로드한다.
4. 업로드 결과를 WAS DB에 저장한다.
   - `fileId`·`namespaceId`·`path`·소유자·생성 시각·`TEMP` 상태를 기록한다.
5. 기록을 완료한 뒤 `fileId`를 반환한다.
6. 제출 요청의 모든 `fileId`를 검증한다.
   - 존재·소유자·namespace·업무 용도·상태를 확인한다.
   - 새로 연결할 파일은 사용 가능한 `TEMP` 상태여야 한다.
   - 수정 시 유지할 파일은 해당 업무 레코드에 이미 연결돼 있어야 한다.
7. 하나의 WAS DB 트랜잭션으로 제출을 확정한다.
   - 업무 레코드와 파일 연결을 저장한다.
   - 새로 연결한 파일을 `TEMP`에서 `ACTIVE`로 바꾼다.
   - DB 작업이 실패하면 업무 레코드·연결·상태 변경을 함께 rollback한다.

제출 처리 중에는 Storix에 업로드하지 않는다.

미제출 `TEMP` 정리:

1. WAS가 `TEMP` 보관 기한을 정한다.
2. 기한이 지난 파일은 새 제출에 연결하지 못하게 한다.
3. cleanup이 대상 상태를 점유해 제출 처리와의 경합을 막는다.
4. 다른 업무 참조가 없는지 확인한다.
5. Storix에 삭제를 요청한다.
   - 실패하면 기록하고 재시도한다.
   - 성공하면 WAS DB 기록을 정리한다.

24시간 보관은 WAS가 선택할 수 있는 정책의 예다.
Storix의 파일 만료 설정과는 별개다.

업로드 중단 정리:

- Storix 저장 성공 후 WAS DB 기록이 실패하거나 프로세스가 중단될 수 있다.
- 먼저 기록한 업로드 시도·경로로 미참조 파일을 찾는다.
- 해당 파일을 삭제한다.
- 미제출 `TEMP` 정리와 별도로 이 cleanup도 수행한다.

### Storix 파일 만료와 확정 계약

새 FILE 생성 시 만료 초를 지정할 수 있다.

| 생성 방식             | 만료 입력          | 필수 생성 조건      |
| --------------------- | ------------------ | ------------------- |
| 조건부 콘텐츠 업로드  | `X-Expires-In`     | `X-If-Absent: true` |
| 재개 업로드 세션 생성 | `expiresInSeconds` | `ifAbsent: true`    |

- 기본 허용 범위는 60~2592000초다.
- 서버 설정으로 범위를 조정할 수 있다.
- FILE 만료 시각은 응답의 `expiresAt`에서 확인한다.
- 업로드 세션의 만료와 완료된 FILE의 만료는 별개다.

기본 확정 순서:

1. FILE 참조를 포함한 자체 영속 상태와 `persist` 재시도 작업을 같은 커밋에 기록한다.
2. 커밋 성공 후 Storix에 확정을 요청한다.
3. 성공할 때까지 저장한 작업을 재시도한다.

자체 상태 commit 전에 만료를 해제하면 commit 실패 후 미참조 파일이 남을 수 있다.

임시 기록을 먼저 저장하는 WAS의 대안 순서:

1. 업로드 직후 경로·node ID를 자체 DB에 임시 기록으로 남긴다.
2. Storix에 확정을 요청한다.
3. 확정 성공 후 업무 데이터와 파일 연결을 commit한다.
4. 기한이 지난 임시 기록을 정리한다.

대안 순서의 조건·실패 처리:

- 임시 기록을 기한 뒤 정리하는 WAS에서만 사용한다.
- 확정에 실패하면 업무 데이터를 commit하지 않는다.
- 업무 데이터가 만료 예정 파일을 참조하지 않게 하는 순서다.
- 확정 후 commit이 실패하면 확정된 파일이 임시 기록으로 남는다.
- 임시 기록 정리 작업이 해당 파일을 삭제한다.
- 만료 전에 완료해야 하는 확정 재시도 작업은 필요하지 않다.

확정 요청:

- API는 `POST /api/v2/namespaces/{namespaceId}/fs/mutations`다.
- 본문은 `{ "kind": "persist", "path": "/example.bin", "ifRevision": "r1.…" }`다.
- `Idempotency-Key`와 `X-Mutation-Scope`가 필요하다.

| 결과                                         | 동작·판정                                                        |
| -------------------------------------------- | ---------------------------------------------------------------- |
| 확정 성공                                    | revision이 바뀌고 `expiresAt`이 null이 된다                      |
| 이미 만료 없음                               | 변경 없이 성공한다                                               |
| 같은 key로 재시도                            | 최초 결과를 재생한다                                             |
| 성공 응답 유실 후 새 key로 재시도해 412 수신 | `current.id`와 `current.expiresAt`으로 확정 완료 여부를 판단한다 |

412를 받았을 때는 `current.id`가 같은 FILE인지 확인한다.
`current.expiresAt`이 null이면 확정 완료로 판정할 수 있다.

만료·GC 규칙:

- 만료 시각이 지나도 GC 삭제 전에는 조회·확정할 수 있다.
- GC 삭제는 namespace의 휴지통 정책을 따른다.
- 휴지통의 기본값은 OFF다.
- 만료를 해제하지 않은 FILE은 GC가 삭제할 수 있다.
- 필요한 FILE의 확정 누락은 데이터 유실로 이어진다.
- PUBLIC namespace의 무인증 콘텐츠 조회·다운로드는 만료 예정 FILE을 404로 숨긴다.

## 기존 첨부파일을 제거할 때

1. WAS DB의 파일 연결 변경을 commit한다.
2. 다른 업무에서 사용하지 않는 파일만 Storix에 삭제 요청한다.
3. 삭제 실패는 재시도할 작업으로 기록한다.

DB commit 전에 파일을 삭제하면 rollback 후 업무 레코드가 삭제된 파일을 가리킬 수 있다.

## Storix API 대응

| 작업                         | API                                                         | 계약                                                  |
| ---------------------------- | ----------------------------------------------------------- | ----------------------------------------------------- |
| 업로드                       | `POST /api/v2/namespaces/{namespaceId}/fs/content?path=...` | 파일 바이트를 받고 성공 응답에 `id`·`path`를 반환한다 |
| 새 파일만 업로드             | `fs/content/conditional`                                    | 조건부 콘텐츠 업로드 계약을 따른다                    |
| 만료 지정                    | `POST .../fs/content/conditional`의 `X-Expires-In`          | 새 FILE 조건에서만 허용한다                           |
| 재개 업로드의 FILE 만료 지정 | `POST .../fs/upload-sessions`의 `expiresInSeconds`          | 새 FILE 조건에서만 허용한다                           |
| 확정                         | `POST .../fs/mutations`의 `persist`                         | `ifRevision`이 일치하는 FILE의 만료를 해제한다        |
| 확인                         | `GET /api/v2/namespaces/{namespaceId}/fs/stat?path=...`     | 현재 `id`를 반환한다                                  |
| 삭제                         | `POST /api/v2/namespaces/{namespaceId}/fs/rm?path=...`      | 경로를 대상으로 Storix 휴지통 계약을 따른다           |

큰 파일의 선 업로드에는 재개 업로드를 사용할 수 있다.
세션 만료는 **완료 전 업로드 세션**에 적용한다.
완료된 FILE의 만료는 별도 `expiresInSeconds` 입력으로 지정한다.
