# WAS와 Storix가 서로를 신뢰하는 방법

WAS는 최종 사용자를 인증하고 파일 접근 권한을 판단합니다. Storix는 요청한 **서비스**를 확인한 뒤 파일을 저장·조회·삭제합니다. 따라서 사용자 로그인 정보나 사용자별 권한을 Storix에 넘겨 서비스 간 인증을 대신하지 마세요.

서비스 간 신뢰에는 두 방향이 있습니다.

| 확인하는 쪽 | 확인할 대상                     | 이유                                                      |
| ----------- | ------------------------------- | --------------------------------------------------------- |
| Storix      | 요청한 쪽이 허용된 WAS인가      | 다른 서비스나 외부 사용자가 보호 API를 호출하지 못하게 함 |
| WAS         | 연결한 서버가 의도한 Storix인가 | API key와 파일을 다른 서버에 보내지 않게 함               |

## 현재 Storix의 기본 방식

Storix 보호 API는 WAS가 보내는 `Authorization: Bearer <STORIX_API_KEY>`를 검사합니다. WAS는 API key를 서버 안에만 보관하고 브라우저에 전달하지 않습니다. Storix의 현재 공유 키는 **키를 알고 있는 호출자**를 허용하지만, 여러 WAS가 같은 키를 쓰면 호출자를 각각 구분하지는 못합니다. 사용자별 파일 권한은 계속 WAS가 검사합니다.

WAS는 Storix 주소를 내부 서비스 주소로 고정하고, 호스트 사이를 통신한다면 HTTPS로 Storix 또는 앞단 프록시의 서버 인증서를 확인하세요. 보호 API는 공개 nginx 경로에 연결하지 마세요. 내부망에 있다는 사실만으로 상대 서비스를 인증했다고 간주하지 않습니다.

## 배포에서 선택할 수 있는 조합

| 조합                                   | 서로를 확인하는 방식                                                        | 사용 시점과 주의점                                                                   |
| -------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 내부 경로 + API key                    | Storix가 API key를 확인. 같은 호스트라면 WAS가 loopback의 Storix에 연결     | 단순한 배포에 적합. 다른 호스트와 통신하면 TLS를 추가해야 함                         |
| HTTPS + API key                        | WAS가 서버 인증서를 확인하고 Storix가 API key를 확인                        | 호스트가 분리된 배포의 기본 선택지. API key는 안전하게 보관·교체해야 함              |
| mTLS + API key                         | 양쪽이 인증서로 연결 상대를 확인하고 Storix가 API key도 확인                | 서비스 신원을 연결 단계에서도 확인하려는 배포에 적합. 인증서 발급·교체 운영이 필요   |
| 서비스 메시 또는 내부 프록시 + API key | 배포 인프라가 서비스 간 mTLS와 접근 경로를 관리하고 Storix는 API key를 확인 | 이미 해당 인프라를 운영할 때 선택. 프록시 뒤 Storix로 우회 접근하는 경로를 막아야 함 |

현재 [내부 mTLS 배포 예시](../deployment/scenarios/co-located-nginx-mtls/README.md)는 WAS가 Nginx의 내부 listener에 클라이언트 인증서를 제시하고, Nginx가 Storix로 전달하는 요청에는 WAS의 API key가 그대로 들어가는 조합입니다. 이 예시에서 **mTLS는 Nginx에서 종료**되고 Storix 애플리케이션은 API key를 검사합니다. Storix가 직접 클라이언트 인증서를 검증하는 기능을 뜻하지 않습니다.

별도의 서비스별 키나 단기 서비스 토큰으로 WAS마다 다른 신원을 부여하는 방법도 있습니다. 현재 Storix는 배포 단위의 공유 API key를 사용하므로, 이런 방법은 기존 설정만 바꾸어 활성화할 수 있는 기능이 아닙니다. 실제로 여러 호출 서비스를 구분해야 할 때 별도 설계가 필요합니다.

## 사용처에서 확인할 원칙

- WAS가 사용자를 확인하고 업무 파일의 소유·접근 권한을 결정합니다. Storix의 API key 또는 mTLS 인증서가 사용자 권한을 뜻하지 않습니다.
- Storix 보호 API는 WAS가 접근하는 내부 경로에 두고, 공개 경로에는 [다운로드 가이드](./was-file-download-patterns.md)의 presigned 객체 다운로드만 둡니다. `PUBLIC` namespace를 쓰는 경우에만 그 공개 읽기 경로를 별도 정책으로 엽니다.
- API key와 클라이언트 인증서의 비밀키는 브라우저, 공개 로그, presigned URL에 포함하지 않습니다.
- 방화벽·내부망·프록시 접근 제한은 호출 가능한 경로를 줄이는 수단입니다. 서비스 신원 확인은 API key나 인증서와 함께 구성합니다.

Storix의 현재 API key 계약은 [서비스 인증 ADR](../../apps/api/docs/adr/0007-service-auth-static-api-key.md)을, 실제 mTLS 연결 예시는 [배포 시나리오](../deployment/scenarios/co-located-nginx-mtls/README.md)를 참고하세요. 네트워크 위치만으로 신뢰하지 않는 원칙은 [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)에 설명돼 있습니다.
