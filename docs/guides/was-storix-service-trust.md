# WAS와 Storix가 서로를 신뢰하는 방법

**사용자 권한은 WAS가 판단하고 서비스 인증은 Storix가 수행한다.**

- WAS가 최종 사용자를 인증한다.
- WAS가 파일 접근 권한을 판단한다.
- Storix가 요청 서비스를 확인한 뒤 파일을 저장·조회·삭제한다.
- 사용자 로그인 정보·사용자별 권한으로 서비스 간 인증을 대신하지 않는다.

서비스 간 확인 방향:

| 확인하는 쪽 | 확인할 대상                     | 목적                                         |
| ----------- | ------------------------------- | -------------------------------------------- |
| Storix      | 요청한 쪽이 허용된 WAS인가      | 외부 사용자·다른 서비스의 보호 API 호출 차단 |
| WAS         | 연결한 서버가 의도한 Storix인가 | 다른 서버로 API key·파일을 보내는 상황 방지  |

## 현재 Storix의 기본 방식

API key 인증:

- Storix 보호 API는 `Authorization: Bearer <STORIX_API_KEY>`를 검사한다.
- WAS는 API key를 서버 안에만 보관한다.
- 브라우저에는 API key를 전달하지 않는다.
- 공유 키는 **키를 아는 호출자**를 허용한다.
- 같은 키를 쓰는 여러 WAS를 각각 구분하지 못한다.
- 사용자별 파일 권한은 WAS가 검사한다.

WAS 연결 규칙:

- Storix 주소를 내부 서비스 주소로 고정한다.
- 호스트 간 통신에는 HTTPS를 사용한다.
- Storix 또는 앞단 프록시의 서버 인증서를 확인한다.
- 보호 API는 공개 nginx 경로에 연결하지 않는다.
- 내부망에 있다는 이유만으로 상대 서비스가 인증됐다고 판단하지 않는다.

## 배포에서 선택할 수 있는 조합

| 조합                                   | 상대 확인                                           | 사용 조건                                  |
| -------------------------------------- | --------------------------------------------------- | ------------------------------------------ |
| 내부 경로 + API key                    | Storix가 API key 확인                               | 같은 호스트의 loopback 연결                |
| HTTPS + API key                        | WAS가 서버 인증서 확인, Storix가 API key 확인       | 호스트가 분리된 배포의 기본 선택지         |
| mTLS + API key                         | 양쪽이 인증서로 상대 확인, Storix가 API key 확인    | 연결 단계의 서비스 신원 확인이 필요한 배포 |
| 서비스 메시 또는 내부 프록시 + API key | 인프라가 mTLS·접근 경로 관리, Storix가 API key 확인 | 해당 인프라를 이미 운영하는 배포           |

조합별 운영 조건:

- 내부 경로만 사용하는 구성도 다른 호스트와 통신하면 TLS를 추가한다.
- API key는 안전하게 보관·교체한다.
- mTLS는 인증서 발급·교체 절차가 필요하다.
- 서비스 메시·프록시 뒤 Storix로 우회 접근하는 경로는 차단한다.

현재 [내부 mTLS 배포 예시](../deployment/scenarios/co-located-nginx-mtls/README.md)의 인증 흐름:

1. WAS가 Nginx 내부 listener에 클라이언트 인증서를 제시한다.
2. Nginx가 클라이언트 인증서를 검증한다.
3. Nginx가 WAS의 API key를 그대로 Storix에 전달한다.
4. Storix 애플리케이션이 API key를 검사한다.

이 예시의 **mTLS는 Nginx에서 종료**된다.
Storix가 직접 클라이언트 인증서를 검증하는 기능은 아니다.

서비스별 신원 분리:

- 별도 서비스별 키·단기 서비스 토큰으로 WAS마다 신원을 부여하는 방법이 있다.
- 현재 Storix는 배포 단위의 공유 API key를 사용한다.
- 서비스별 신원 분리는 기존 설정만으로 활성화할 수 없다.
- 여러 호출 서비스를 구분해야 하면 별도 설계가 필요하다.

## 사용처에서 확인할 원칙

사용자·서비스 권한:

- WAS가 업무 파일의 소유·접근 권한을 결정한다.
- Storix API key·mTLS 인증서는 사용자 권한을 뜻하지 않는다.

공개 경로:

- Storix 보호 API는 WAS가 접근하는 내부 경로에 둔다.
- 공개 경로에는 [다운로드 가이드](./was-file-download-patterns.md)의 presigned 객체 다운로드만 둔다.
- `PUBLIC` namespace의 공개 읽기는 별도 정책으로 연다.

자격증명·접근 제한:

- API key·클라이언트 인증서 비밀키는 브라우저·공개 로그·presigned URL에 포함하지 않는다.
- 방화벽·내부망·프록시는 호출 가능한 경로를 제한한다.
- 접근 제한과 함께 API key 또는 인증서로 서비스 신원을 확인한다.

참조:

- API key 계약: [서비스 인증 ADR](../../apps/api/docs/adr/0007-service-auth-static-api-key.md).
- mTLS 연결: [배포 시나리오](../deployment/scenarios/co-located-nginx-mtls/README.md).
- 네트워크 위치만으로 신뢰하지 않는 원칙: [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final).
