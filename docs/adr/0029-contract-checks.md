# 공개 HTTP 계약은 실제 서버에 실행하는 contract 검증으로 고정한다

## 상태

승인됨 (2026-09-29)

## 배경

- 에이전트 작업 중 구현이 소비자에게 약속한 동작에서 벗어날 수 있다.
- 기존 `*.integration-spec.ts`는 테스트 프로세스 안에서 Nest 모듈을 조립한다(`createNestApplication`).
  - 빌드된 서버를 별도 프로세스로 기동해 공개 API를 호출하지 않는다.
- `docs/requirements/file-storage.md`의 수용 조건·판정 근거는 산문이다.
  - 코드와 기계적으로 연결되지 않는다.
- 과거 xio 라이브러리 프로젝트의 scenario 방식이 같은 문제를 해결했다.
  - 사용처 관점의 실행 가능한 명세였다.

## 결정

- 계약 검증은 `apps/contract`에 둔다.
- 계약은 공개 HTTP만 호출한다.
- 각 계약은 대응하는 `RQ-NNN`을 선언한다.
- 용어는 `contract`를 쓴다.
  - `scenario`는 `docs/deployment/scenarios/`의 배포 예시 용어다.
- 서버는 프로필(기동 설정)마다 한 번 기동한다.
- 계약마다 새 namespace로 상태를 격리한다.
- 빌드된 `apps/api/dist/main.js`를 별도 프로세스로 기동한다.
- blob 저장소는 VersityGW 컨테이너 하나를 쓴다.
- 기본 DB는 SQLite다.
- Postgres 실행은 러너 옵션으로 추가한다.
- 계약 변경의 사용자 승인 규칙은 `AGENTS.md`에 둔다.

## 대안

- 계약마다 서버 재기동.
  - 기동 비용이 계약 수에 비례해 늘어난다.
- N개 계약마다 서버 재시작.
  - 재시작 경계가 임의적이다.
  - 재시작은 기동 설정이 다르거나 재시작 자체를 검증할 때 필요하다.
- 메모리 S3 스텁.
  - 실제 백엔드와 다르면 계약이 스텁의 동작을 검증하게 된다.
- 컨테이너 이미지 기동.
  - 배포 형태와 같다.
  - 이미지 빌드 비용이 든다.
  - 필요해지면 러너 옵션으로 추가한다.
- 기존 integration-spec 확장.
  - 테스트 프로세스 안의 Nest 모듈 조립에 의존한다.
  - 배포 형태의 서버를 검증하지 못한다.

## 결과

- 계약과 RQ는 `rq` 필드로 연결한다.
- `pnpm contract --coverage`는 계약 없는 RQ를 출력한다.
- 계약이 실패하면 구현을 고친다.
- 계약을 바꾸려면 사용자 승인이 필요하다.
- 러너는 docker를 요구한다.
- 결정 시점에 구현된 드라이버는 SQLite뿐이다.
