# 공개 HTTP 계약은 실제 서버에 실행하는 contract 검증으로 고정한다

## 상태

승인됨 (2026-09-29)

## 배경

- 에이전트와 작업하면 구현이 소비자에게 약속한 동작에서 벗어나는 일이 생긴다.
- 기존 `*.integration-spec.ts`는 테스트 프로세스 안에서 Nest 모듈을 조립해(`createNestApplication`) 검증한다. 빌드된 서버를 프로세스로 기동해 공개 API를 호출하지 않는다.
- `docs/requirements/file-storage.md`의 수용 조건과 판정 근거는 산문이라 코드와 기계적으로 연결되지 않는다.
- 과거 xio 라이브러리 프로젝트의 scenario 방식(사용처 관점의 실행 가능한 명세)이 같은 문제를 풀었다.

## 결정

- `apps/contract`에 계약 검증을 둔다. 계약은 공개 HTTP만 호출하고 각 계약은 대응하는 `RQ-NNN`을 선언한다.
- 용어는 `contract`다. `scenario`는 `docs/deployment/scenarios/`에서 배포 예시를 뜻하므로 쓰지 않는다.
- 서버는 계약마다 기동하지 않고 프로필(기동 설정) 단위로 한 번 기동한다. 계약마다 새 namespace를 만들어 상태를 격리한다.
- 서버는 빌드된 `apps/api/dist/main.js`를 프로세스로 기동한다. blob 저장소는 VersityGW 컨테이너 하나다.
- 기본 DB는 SQLite다. Postgres 실행은 러너 옵션으로 추가한다.
- 계약 변경은 사용자 승인을 받는 규칙을 `AGENTS.md`에 둔다.

## 대안

- 계약마다 서버 재기동: 계약 수에 비례해 느리다.
- N개 계약마다 재시작: 재시작 경계가 임의적이다. 재시작이 필요한 이유는 기동 설정 차이와 재시작 자체의 검증뿐이다.
- 메모리 S3 스텁: 스텁이 실제 백엔드와 다르면 계약이 스텁을 검증한다.
- 컨테이너 이미지 기동: 배포 형태와 같지만 이미지 빌드가 느리다. 필요해질 때 러너 옵션으로 추가한다.
- 기존 integration-spec 확장: 테스트 프로세스 안 Nest 모듈 조립에 의존하므로 배포 형태의 서버를 검증하지 못한다.

## 결과

- 계약과 RQ가 `rq` 필드로 연결된다. `pnpm contract --coverage`가 계약 없는 RQ를 출력한다.
- 계약이 실패하면 구현을 고치는 것이 기본이다. 계약을 바꾸려면 승인이 필요하다.
- 러너는 docker를 요구한다. 이 결정 시점에 구현된 드라이버는 SQLite뿐이다.
